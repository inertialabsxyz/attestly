# AWP ↔ SR 11-7 Pre-Mapping

> **Status:** Decision-support draft. Not legal advice. Read alongside the [`KYC receipts demo`](../../examples/kyc_receipts.rs) and the audit viewer at [`tools/audit-viewer/`](../../tools/audit-viewer/).

## (a) Preamble

**SR 11-7** is the US Federal Reserve's Supervisory Letter SR 11-7, *"Guidance on Model Risk Management,"* issued April 4, 2011 jointly with OCC Bulletin 2011-12. It is the de-facto US standard for how regulated financial institutions govern the models they rely on. Although the 2011 text predates modern AI agents, US bank examiners now treat it as the controlling reference for AI / agentic systems whose outputs influence regulated decisions (lending, KYC, fraud, capital, claims). State insurance regulators and the OCC have since echoed its three-pillar framing — **development**, **validation**, and **governance** — in subsequent guidance.

For agent-driven decisions ("approve this loan," "flag this transaction," "deny this claim"), SR 11-7 applies because the agent *is* the institution's model in the eyes of an examiner. The examiner will ask: who built the model, how do you know it works, who watches it in production, and **can you prove what it actually did on a given case**?

AWP addresses one strand of that last question. AWP attests to **what an agent did** on a specific input — the input it saw, the output it produced, when, signed by which agent's key, and (when a Verifier ran) what an independent re-decision concluded. It does **not** attest to whether the underlying model is fit for purpose under SR 11-7's broader requirements, and it cannot substitute for model validation, monitoring, governance, or change control. AWP is one control among many in an SR 11-7-aligned program — specifically, the *agent decision provenance* control.

## (b) Scope and limits

**What AWP attestations help with:**

- **Non-repudiable record of agent decisions.** Each `Attestation` is signed with the agent's ed25519 keypair and the signature covers `agent_id`, `agent_pubkey`, `task_hash`, `output_hash`, `output`, `status`, `references`, and `timestamp` ([`crates/awp-core/src/attestation.rs`](../../crates/awp-core/src/attestation.rs)).
- **Independent verification by a second agent.** A `Verifier` cryptographically checks the Worker's attestation and then independently re-runs the decision rule, emitting `AttestationStatus::Verified { attestation_valid, answer_correct }` ([`crates/awp-agents/src/verifier.rs`](../../crates/awp-agents/src/verifier.rs), [`crates/awp-agents/src/kyc_agents.rs`](../../crates/awp-agents/src/kyc_agents.rs)). Tamper or worker disagreement flips one of the two flags to `false` and is surfaced in the receipt.
- **Durable audit trail.** Every Worker and Verifier attestation is appended to `data/attestations.json` and joined to a `TaskExecution` row in `data/executions.json` ([`crates/awp-core/src/execution.rs`](../../crates/awp-core/src/execution.rs)).
- **Cryptographic timestamps.** Each attestation carries a Unix-epoch `timestamp` covered by the signature. AWP does not anchor these to a third-party time service; the timestamp is the agent's own clock at signing time.
- **Batched inclusion proofs for efficient long-term storage.** Attestations can be batched into a Merkle tree; a per-attestation `InclusionProof` lets anyone verify membership against the batch root without holding the whole batch ([`crates/awp-core/src/merkle.rs`](../../crates/awp-core/src/merkle.rs), [`crates/awp-core/src/storage.rs`](../../crates/awp-core/src/storage.rs)).
- **Optional parallel verification.** N verifiers can run concurrently against one worker attestation, with disagreement among verifiers detected and logged ([`crates/awp-agents/src/parallel.rs`](../../crates/awp-agents/src/parallel.rs)).

**What AWP attestations do *not* address:**

Model validation methodology, ongoing performance monitoring, governance committee structures, change management, risk appetite frameworks, third-party model risk, stress testing, model inventory, conceptual soundness review, benchmarking against alternatives, sensitivity / stability analysis, bias and fairness assessment, vendor due diligence, and data quality controls. Each of these is a first-class SR 11-7 expectation; none is in AWP's scope. See section (e).

**Recommended posture:** AWP is one of multiple controls in an SR 11-7-aligned model risk management program. It is the *agent decision provenance* control specifically — useful when an examiner asks *"prove this agent saw this input and emitted that decision, on this date, signed by this agent"*. It is not useful for *"prove this model is fit for purpose"*.

## (c) Clause-by-clause mapping

| SR 11-7 section | Requirement summary | AWP feature(s) that help | Necessary-but-not-sufficient? | Notes |
|---|---|---|---|---|
| **III. Model Development, Implementation, and Use** — *Documentation* | Models, including their use, must be supported by detailed documentation enabling parties unfamiliar with the model to understand how the model operates and is used. | The receipt's `task_hash` + `output` + `output_hash` + `agent_pubkey` + `timestamp` collectively document a single use of the model. The audit viewer renders the receipt human-readably ([`tools/audit-viewer/index.html`](../../tools/audit-viewer/index.html)). | **Y** | AWP documents *each invocation*, not the model design, training data, theoretical basis, or limitations. Those remain the institution's own documentation responsibility. |
| **III. Model Development, Implementation, and Use** — *Ongoing use* | Effective controls should ensure the model is used as intended; deviation from intended use should be detected. | A Verifier re-running the deterministic decision rule against the same input is a per-invocation control: if the worker's emitted decision differs from the verifier's independent re-decision, `answer_correct` flips to `false` ([`crates/awp-agents/src/kyc_agents.rs`](../../crates/awp-agents/src/kyc_agents.rs) — `KycVerifier::run`). | **Y** | This catches per-invocation tamper or runtime divergence between two agents executing the same rule. It does not detect drift in the underlying *rule* over time, nor does it validate that the rule itself is the intended one. |
| **III. Model Development, Implementation, and Use** — *Process verification* | Processes should be in place to verify that all model components — inputs, processing components, outputs — are functioning as designed. | The Verifier cryptographically checks the Worker's attestation (`attestation_valid`) and re-derives the output to check semantic correctness (`answer_correct`). Both flags ride on the Verifier's signed attestation ([`crates/awp-core/src/attestation.rs`](../../crates/awp-core/src/attestation.rs) — `AttestationStatus::Verified`). | **Y** | Verifies that the *recorded* invocation is internally consistent and reproducible. Does not verify the design of inputs, processing, or outputs in isolation. |
| **IV. Model Validation** — *Outcomes analysis* | Outcomes analysis compares model outputs to corresponding actual outcomes; ongoing monitoring should include process verification and benchmarking. | Verifier disagreement detection ([`crates/awp-agents/src/dispatcher.rs`](../../crates/awp-agents/src/dispatcher.rs), [`crates/awp-agents/src/parallel.rs`](../../crates/awp-agents/src/parallel.rs)) provides one form of process-verification benchmarking: a second independent agent's decision against the same input. | **Y** | This is *agent-vs-agent* benchmarking on the same rule — not *model-vs-real-outcome* analysis. SR 11-7 outcomes analysis primarily means comparing predictions to ground truth observed later; AWP does not capture ground truth and does not perform that comparison. |
| **IV. Model Validation** — *Independent review* | Validation activities should be conducted by staff with appropriate incentives, competence, and influence — independent from model development and use. | When the Worker and Verifier are operated by separately-keyed agents (distinct `agent_pubkey`s, ideally distinct teams), the Verifier's attestation is cryptographically attributable to that independent party ([`crates/awp-agents/src/verifier.rs`](../../crates/awp-agents/src/verifier.rs)). | **Y** | AWP enforces *cryptographic* independence (different keys produce different signatures); it cannot enforce *organisational* independence (the same person could control both keys). Organisational independence is a governance control, not a cryptographic one. Today's prototype generates a fresh keypair per process (`AgentKeypair::generate` in [`crates/awp-core/src/signing.rs`](../../crates/awp-core/src/signing.rs)); a planned persistent-identity store will make the attribution stable across runs (gap tracked in [`../USER_JOURNEYS.md`](../USER_JOURNEYS.md)). |
| **V. Governance, Policies, and Controls** — *Documentation of model risk management* | Documentation of model risk management activities should include policies, procedures, and the results of model risk management activities. | The persistent JSONL logs and SQLite store are durable evidence of *what model risk management activities ran on which inputs*: every `TaskExecution` and every produced `Attestation` is preserved with cryptographic integrity ([`crates/awp-core/src/execution.rs`](../../crates/awp-core/src/execution.rs), [`crates/awp-core/src/storage.rs`](../../crates/awp-core/src/storage.rs)). | **Y** | AWP captures the *machine-generated artefacts* of one specific control (per-invocation verification). It does not capture human-authored policies and procedures. |
| **V. Governance, Policies, and Controls** — *Internal audit* | Internal audit should evaluate whether model risk management is comprehensive, rigorous, and effective. | Inclusion proofs ([`crates/awp-core/src/merkle.rs`](../../crates/awp-core/src/merkle.rs) — `verify_inclusion`) let internal audit sample any individual attestation and prove it was part of a batch whose root the institution committed to, without needing the entire batch. | **Y** | AWP gives internal audit a tamper-evident sample-and-verify primitive. The audit's *judgement* — whether the program is comprehensive, rigorous, and effective — is human work AWP does not perform. |
| **V. Governance, Policies, and Controls** — *Maintenance of records* | Records should be maintained sufficiently to support reconstruction of the model and its uses. | The append-only JSONL logs plus the Merkle batch store provide a tamper-evident record of every agent invocation; signatures bind each receipt to the agent's public key, and batch roots bind the full set ([`crates/awp-core/src/attestation.rs`](../../crates/awp-core/src/attestation.rs), [`crates/awp-core/src/storage.rs`](../../crates/awp-core/src/storage.rs)). | **Y** | AWP records *uses of the model*. Reconstruction of *the model itself* (its rule, code, weights, config) requires the institution's own version control and model inventory. |

Every row above is marked **Necessary-but-not-sufficient: Y**. The honest framing is that AWP attestations are an **input** to compliance with each of these clauses — they provide cryptographic evidence the institution would otherwise lack — but no clause in SR 11-7 is fully discharged by AWP alone. A row marked **N** would imply AWP fully satisfies the clause; we are not aware of any clause for which that is defensible.

## (d) Sample audit narrative

**Setting.** A US-regulated mid-market bank deploys an automated KYC decision agent. During a routine examination, the examiner says: *"Show me how you ensure your KYC agent's decisions are auditable and verifiable."*

**The Risk Officer's answer.** "We can show you any individual KYC decision the agent has made and prove three things: that the input was exactly what we say it was, that the decision was exactly what we say it was, and that an independent second agent reviewed the same input and reached the same conclusion."

The Risk Officer opens [`tools/audit-viewer/index.html`](../../tools/audit-viewer/index.html), drags in the day's `attestations.json` and `executions.json`, and walks the examiner through one row:

```
Customer #4711 — Decision: APPROVE
Worker:    agent-kyc-01  signature ✓
Verifier:  agent-kyc-02  signature ✓  verdict ✓
Receipt:   ./data/attestations.json (id: ...)
Audit-ready: yes
```

She clicks the row. The viewer expands to show the full signed `Attestation` payload, the verifier's verdict (`Verified { attestation_valid: true, answer_correct: true }`), and both agents' truncated public keys. She notes that the page itself re-verified the ed25519 signatures in the browser — *"trust nothing, verify everything"* — and that the same JSONL files would verify identically on the examiner's own laptop.

She then opens the SQLite store and demonstrates a Merkle inclusion proof for the same attestation: given only the receipt's hash, the proof path, and the batch root the bank publishes weekly, the examiner can confirm the receipt was part of that batch — no other receipts revealed.

**What the examiner still needs to see beyond AWP.** AWP demonstrates that the agent's decisions are *captured truthfully and verifiably*. It does **not** demonstrate that the agent is *the right model for KYC*. To complete the SR 11-7 picture the examiner will still ask for: the model validation report on the KYC rule itself (who designed it, against what benchmark, with what conceptual basis), the ongoing-monitoring evidence (false-positive and false-negative rates over time, drift metrics), the governance documentation (who approved deploying this agent, who approves changes, what the change-control workflow is), the third-party risk assessment if any vendor LLM or service is in the loop, and the model inventory entry. The honest framing the Risk Officer uses: *"AWP is our agent decision provenance control. These other artefacts are our other controls. Together they are the program."*

## (e) What AWP does not provide

AWP attests to agent-execution events. It is silent on most of what SR 11-7 requires. The list below is not exhaustive but captures the requirements buyers most often expect a compliance-adjacent tool to address.

- **Model validation methodology.** SR 11-7 §IV requires that models be subject to formal validation — conceptual soundness, ongoing monitoring, outcomes analysis. AWP does not address *how the rule was chosen*, *what alternatives were considered*, or *whether the rule is appropriate for its stated use*. This is typically the work of a separate model validation function (often a Model Risk Management group reporting independently of the model owners).
- **Ongoing model performance monitoring.** Drift, accuracy over time, calibration, false-positive/false-negative rates, population-stability indices — none of these are derivable from AWP attestations. Performance monitoring requires comparing decisions to *ground-truth outcomes*, which AWP does not capture. Observability platforms (Evidently, Fiddler, Arize, internal dashboards, etc.) are the typical control here.
- **Governance committee structures.** SR 11-7 §V expects a governance framework with clearly defined roles: model owner, validator, internal audit, board oversight. AWP does not encode role assignments, approvals, or escalation paths. Governance is a policy-and-process control implemented in committees, RACI matrices, and workflow tools.
- **Change management.** SR 11-7 §V expects controlled change. AWP can attest *that* a particular agent (identified by `agent_pubkey`) executed at a particular time, but it does not approve or restrict changes to the underlying decision rule. A version of the rule could change between attestations and AWP would not detect it. Change management requires version control of the rule itself, a deployment pipeline with sign-offs, and a model inventory with version history — none of which AWP provides.
- **Third-party model risk.** When the agent uses a vendor LLM, MCP tool, or external scoring service, SR 11-7 expects vendor due diligence and ongoing monitoring of the vendor's risk. AWP attests to *use* of whatever the agent invoked; it does not assess the vendor's controls, SOC 2 posture, model card, or contractual obligations. Third-party risk management programs are the relevant control.
- **Risk appetite frameworks.** Boards and senior management are expected to set risk appetite for model use. AWP does not encode appetite or thresholds; it does not refuse decisions that breach appetite.
- **Stress testing and sensitivity analysis.** SR 11-7 §IV expects models to be tested under adverse and outlier conditions. AWP does not generate stress scenarios; it only records what the agent did when invoked.
- **Model inventory.** SR 11-7 expects institutions to maintain a comprehensive inventory of all models in use. AWP can supply *evidence-of-use* for individual models but does not constitute the inventory itself.
- **Conceptual soundness review.** AWP does not assess whether the rule's logic is theoretically appropriate; it records that the rule, as coded, was executed.
- **Bias and fairness assessment.** SR 11-7 (and its post-2011 reinterpretations) expect attention to disparate impact and fairness. AWP records decisions but does not analyse them across protected classes.
- **Data quality controls.** SR 11-7 §III calls out the importance of data quality. AWP commits to the bytes the agent saw, but does not assess whether those bytes are accurate, complete, or representative.

For each of these, the standard institutional posture is: *AWP supplies the per-decision evidence; the listed control supplies what AWP does not.* Neither replaces the other.
